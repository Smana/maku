# agent-factory

The umbrella chart: `maku` and `maku-factory` (`file://`), plus what a plain kind or k3d cluster lacks.

## The contract

| Part | What it means |
|---|---|
| Production-safe defaults | `values.yaml` is a skeleton that renders nothing on its own. `profile` is required: `demo`, or `production`, which fails closed until its seams arrive in v4 rollout steps 2 to 6 |
| The demo | `-f values-demo.yaml` carries every demo default and `profile: demo`. `--set profile=demo` alone fails with `profile demo needs -f values-demo.yaml` |
| The schema | `values.schema.json` rejects unknown top-level keys (a typo like `postgress:`) and malformed values: an unknown profile, `tls.days` below 1, a Postgres image without a digest, a storage size that is not `<n>Mi`, `Gi` or `Ti` |
| The CRDs | [`agent-factory-crds`](../agent-factory-crds/README.md) is installed first. It upgrades the CRDs with every tool and keeps them on uninstall. The subcharts keep their own `crds/` until rollout step 8, so a GitOps tool skips them: Argo CD `skipCrds: true`, Flux `crds: Skip`. An existing cluster adopts its CRDs first: [docs/upgrading.md](../../docs/upgrading.md#adopting-the-crds) |
| The support floor | `kubeVersion: ">=1.30.0-0"` in this chart and both subcharts. Helm 3.15 or later: Helm 3.14 assumes Kubernetes 1.29 when it renders offline, so its `helm template` needs `--kube-version` |
| Stability | Values may still change in a 0.x minor until v4.0.0, each change with a section in [docs/upgrading.md](../../docs/upgrading.md). From v4.0.0, a breaking value change happens only in a major version |

```bash
helm install af-crds charts/agent-factory-crds -n maku --create-namespace
helm install af charts/agent-factory -n maku -f charts/agent-factory/values-demo.yaml -f values-mine.yaml
```

From the OCI registry, the chart carries `values-demo.yaml`:
`helm pull oci://ghcr.io/smana/charts/agent-factory --version <version> --untar`.

## What it adds

The demo adds what a plain kind or k3d cluster lacks:

- the broker's TLS, generated by Helm (`genCA`, `genSignedCert`): Secrets `room-broker-tls`,
  `room-broker-ca` and the factory's broker CA Secret, all kept across upgrades;
- a single-replica Postgres (`rooms-db`, 1Gi PVC) with the roles `rooms_owner`, `rooms_broker`,
  `rooms_retention`, the database `rooms`, and the DSN Secrets `rooms-owner-dsn`, `rooms-broker-dsn`
  and `rooms-retention-dsn` (`sslmode=disable`: the hop stays inside the cluster). The last feeds the
  daily retention CronJob, `room-broker-retention`.

The bundled Postgres is demo-only (v4 D9), behind `postgres.enabled`: `values.yaml` turns it off,
`values-demo.yaml` on, and any profile but `demo` with it on fails the render. To bring your own
Postgres 16 or later, even under the demo, set `postgres.enabled: false`, create the three roles and
their DSN Secrets as [the database](../../docs/database.md) says, and keep the Secret names under
`maku.broker.database`. `task chart:install:k3d:external-db` proves it on k3d against a plain
`postgres:16` outside the chart.

`networkPolicies.plain` (default true) renders two plain NetworkPolicies: `rooms-db` admits 5432 only from
the broker's and the retention job's pods, and the factory's pod admits the broker to the API port (8082) and anyone to the ops/probe port (9090); the intake port (8080) is closed, as the demo configures none. Egress is untouched (runs need GitHub
and the model). The install test asserts a run-labelled pod in `agents` cannot reach `rooms-db` on both
k3d (kube-router) and kind v0.33 (kindnet enforces NetworkPolicy; the test only notes it, not fails, if a kind node does not).

`--set maku.networkPolicies.mode=kubernetes` confines the runs too, on a CNI that enforces
NetworkPolicy: default-deny in `agents`, one NetworkPolicy per run, and the egress proxy holding each
run's HTTPS to its own hosts ([the network modes](../../docs/security.md#the-run-paths-network-modes)).
The run controller's preflight then refuses runs until it proves the CNI enforces them. The demo's
`maku.broker.database.podLabels` lets the broker's policy reach `rooms-db`. `task chart:install:k3d:netpol`
proves both outcomes on k3d: kube-router enforcing (the preflight passes) and a k3s started with
`--disable-network-policy` (it refuses runs).

`values-demo.yaml` (`profile: demo`) makes it the laptop demo: no Cilium (`maku.networkPolicies.enabled: false`), the broker
in local human mode with the apiserver vouching for runs and for the factory (`system:factory`), runc
(`allowUnsandboxed`), the portable `maku.ogenki.io` runs group, and a one-replica factory in `demo`
mode on one GitHub App (`maku-factory.apps.merger.mode: factory` folds the merger into it; a
production install runs two Apps, see [GitHub Apps](../../docs/github-apps.md)). The two Secrets come
from `demo.model` (`agent-model`, in the runs namespace) and `demo.githubApp` (`agent-factory-github`,
or the name in `maku-factory.apps.factory.existingSecret`), or exist already (`existingSecret`, which
must carry the name the subchart reads). `agent-git` and `agent-git-read` (the run tokens) are the factory's to write. To point it at your repository, copy
[`values-mine.example.yaml`](values-mine.example.yaml): Helm replaces a list whole, so a values file
must restate the whole `maku-factory.config.repositories[0]` entry, not one field of it. The
placeholders to change are `name` (`owner/repo`), `maintainers`, `merge.mergerLogin`,
`merge.requiredChecks`, `merge.verifyChecks` and `merge.leakScanCheck` (`ci`), plus `factoryLogin` and
`agentsLogin` (the App's `<slug>[bot]`). The demo loop is scoper, implementer, completion judge,
reviewer, gate (`maku-factory.config.loops`). Its classes are in shadow and `merge.approveToMerge` is
on: the factory merges nothing on its own, and a maintainer's approval of the current head is the
merge (the merger merges that head, as a human merge with no automatic revert). With it off, the room
shows the approval (`maintainer_approved`) and a maintainer merges on GitHub.

## The model gateway

Two optional subcharts, both off by default, put agentgateway in front of the models
([docs/gateway.md](../../docs/gateway.md)):

- `maku-gateway.enabled: true` renders the Gateway `model-gateway`, its identity policies, one backend
  and one route per model alias, the price catalog and the proxy's NetworkPolicy. Its `runs` must equal
  `maku.runs`, and its `broker.serviceAccount` must be `room-broker`: the render fails otherwise.
- `agentgateway.enabled: true` installs the upstream controller, v1.6.0 by digest, restricted, with
  limits. Leave it off where the cluster already runs one.

The CRDs come first. agentgateway's are applied apart from any Helm release: the four of them hold
2.3 MB of schema, and Helm stores a release's chart and manifest in one Secret capped at 1 MiB, which
they would nearly fill. They outlive an uninstall only while nothing prunes them. The Flux and Argo CD
forms, and the upstream `agentgateway-crds` chart as an alternative, are in
[docs/gateway.md](../../docs/gateway.md#agentgateways-crds). Gateway API's standard CRDs (v1.2 or
later) are a cluster prerequisite:

```bash
helm install af-crds charts/agent-factory-crds -n maku --create-namespace
kubectl apply --server-side -f config/agentgateway   # agentgateway v1.6.0's CRDs, apart from any release
helm install af charts/agent-factory -n maku -f charts/agent-factory/values-demo.yaml -f values-mine.yaml \
  --set agentgateway.enabled=true -f my-gateway-values.yaml
```

Runs call the gateway with `maku.runController.model.mode: gateway`, which then needs
`maku-gateway.enabled` or an external `model.gateway.service`. The run controller's aliases, ports and
audience prefix must match `maku-gateway`'s, or the render fails. `values-demo-gateway.yaml`, layered on
`values-demo.yaml`, is the demo in that mode: the demo key becomes the provider's Secret `demo-model` in
the release namespace, and no `agent-model` exists. The planner keeps its URL until the broker's
gateway mode arrives. `task chart:gateway:k3d` proves the gateway on
k3d. agentgateway is vendored (the controller chart under `vendor/`, its CRDs in `config/agentgateway`) and
pinned in `hack/agentgateway.sha256`, which `task chart:deps` checks: no install needs the network for it.

## Spec-intake k3d test

`task chart:intake:k3d` (Docker with buildx, k3d, Helm, kubectl, Go, OpenSSL, curl and jq) builds the
broker, run controller, factory and test-stub images, creates the unique `maku-intake-k3d` cluster with
a private temporary kubeconfig, and proves the planner's ranked `g1` marker, candidate/new hash,
accept-the-rest with an unchanged model counter, and final `unresolved_marker` refusal. It then drives
the scoper's question and ready handoffs, structured `room_brief`, body-only `need_answer`, stale
body/label conflict refusal, and one stable status-comment ID across generations.

The test values use OIDC and the in-cluster stub for every GitHub, ZITADEL and model call. A bare Git
repository serves the harness's clone inside the cluster. All TLS keys, App keys and tokens are
throwaway files in the temporary directory; no real credentials or external writes are used. Failure
prints pod, event and log diagnostics. Success and failure both stop port-forwards, delete the cluster
and remove the temporary credentials.

The scenario is intentionally opt-in, not part of `task check` or the PR demo workflow: building the
images and importing the release harness (about 1.5 GB) makes it too slow for every PR.

Not for production: no backups, no HA, no database TLS.
`clusterDomain` must equal `maku.clusterDomain` and `maku-factory.clusterDomain`.
