# agent-factory

The umbrella chart for a plain kind or k3d cluster. It depends on `maku` and `maku-factory` (`file://`)
and adds what such a cluster lacks:

- the broker's TLS, generated by Helm (`genCA`, `genSignedCert`): Secrets `room-broker-tls`,
  `room-broker-ca` and the factory's broker CA Secret, all kept across upgrades;
- a single-replica Postgres (`rooms-db`, 1Gi PVC) with the roles `rooms_owner`, `rooms_broker`,
  `rooms_retention`, the database `rooms`, and the DSN Secrets `rooms-owner-dsn` and `rooms-broker-dsn`
  (`sslmode=disable`: the hop stays inside the cluster).

`networkPolicies.plain` (default true) renders two plain NetworkPolicies: `rooms-db` admits 5432 only from
the broker's pods, and the factory's pod admits the broker to the API port (8082) and anyone to the ops/probe port (9090); the intake port (8080) is closed, as the demo configures none. Egress is untouched (runs need GitHub
and the model). The install test asserts a run-labelled pod in `agents` cannot reach `rooms-db` on both
k3d (kube-router) and kind v0.33 (kindnet enforces NetworkPolicy; the test only notes it, not fails, if a kind node does not).

`profile: demo` makes it the laptop demo: no Cilium (`maku.networkPolicies.enabled: false`), the broker
in local human mode with the apiserver vouching for runs and for the factory (`system:factory`), runc
(`allowUnsandboxed`), the portable `maku.ogenki.io` runs group, and a one-replica factory in `demo`
mode on one GitHub App. The two Secrets come from `demo.model` (`agent-model`, in the runs namespace)
and `demo.githubApp` (`agent-factory-github`), or exist already (`existingSecret`, which must carry the
name the subchart reads). `agent-git` is the factory's to write. To point it at your repository, copy
[`values-mine.example.yaml`](values-mine.example.yaml): Helm replaces a list whole, so a values file
must restate the whole `maku-factory.config.repositories[0]` entry, not one field of it. The
placeholders to change are `name` (`owner/repo`), `maintainers`, `merge.mergerLogin`,
`merge.requiredChecks`, `merge.verifyChecks` and `merge.leakScanCheck` (`ci`), plus `factoryLogin` and
`agentsLogin` (the App's `<slug>[bot]`). The demo loop is scoper, implementer, completion judge,
reviewer, gate (`maku-factory.config.loops`). Its classes are in shadow and `merge.approveToMerge` is
on: the factory merges nothing on its own, and a maintainer's approval of the current head is the
merge (the merger merges that head, as a human merge with no automatic revert). With it off, the room
shows the approval (`maintainer_approved`) and a maintainer merges on GitHub. An unset `profile` fails: production values arrive with stage 2.

## Spec-intake k3d test

`task chart:intake:k3d` (Docker with buildx, k3d, Helm, kubectl, Go, OpenSSL, curl and jq) builds the
broker, run controller, factory and test-stub images, creates the unique `maku-intake-k3d` cluster with
a private temporary kubeconfig, and proves the planner's ranked `g1` marker, candidate/new hash,
accept-the-rest with an unchanged model counter, and final `unresolved_marker` refusal. It then drives
the scoper's question and ready handoffs, structured `room_brief`, body-only `need_answer`, stale
body/label conflict refusal, and one stable status-comment ID across generations.

The test values use OIDC and the in-cluster stub for every GitHub, ZITADEL and model call. A bare Git
repository serves the harness's clone inside the cluster. All TLS keys, App keys and tokens are
throwaway files in the temporary directory; no real credentials or external writes are used. Failure
prints pod, event and log diagnostics. Success and failure both stop port-forwards, delete the cluster
and remove the temporary credentials.

The scenario is intentionally opt-in, not part of `task check` or the PR demo workflow: building the
images and importing the release harness (about 1.5 GB) makes it too slow for every PR.

Not for production: no backups, no HA, no database TLS.
`clusterDomain` must equal `maku.clusterDomain` and `maku-factory.clusterDomain`.
