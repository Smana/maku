# agent-factory-crds

The agent factory's six CustomResourceDefinitions (`maku.ogenki.io`): Rooms, AgentRuns, Tasks,
Factories, Repositories and MergePolicies. Install it before `agent-factory`.

The CRDs are templates, not `crds/`: Helm, Flux and Argo CD all upgrade a template, while Helm never
upgrades what sits in `crds/`. Each CRD carries `helm.sh/resource-policy: keep`, so uninstalling this
chart leaves the CRDs, and every Room and Task, in place. `keep: false` drops the annotation: an
uninstall then deletes every Room and Task.

It also holds the cluster's shared ClusterRoles (D2, step 7 R10), one set for every install:
`maku-factory-admin`, `maku-mergepolicy-editor` and `maku-viewer`, aggregated into the built-in
`admin`, `edit` and `view` roles, and `agent-factory-flux-reader`, which each install's factory binds
for a class's `monitor.flux`. They are kept on uninstall as the CRDs are. `clusterRoles: false` leaves
them out.

The CRDs are generated by controller-gen into `config/crd/`; `task crd:gen` copies them into `files/`
and `task crd:check` fails on any drift.

```bash
helm install af-crds oci://ghcr.io/smana/charts/agent-factory-crds --version <version>
```

## MergePolicy's two shapes

This release's `MergePolicy` CRD admits two shapes. The per-repository shape has `spec.repositoryRef`,
`classes` and `merge`. The class shape is one reusable class definition, named by the object, that a
`Repository` binds under `spec.mergePolicies`. CEL keeps the two shapes apart. The next minor
removes the per-repository fields from the schema, and the API server then prunes them on read.
Before you upgrade to it, check that no MergePolicy still has a `repositoryRef`:

```bash
kubectl get mergepolicy -A -o jsonpath='{..repositoryRef}'
```

`kubectl get repository` shows `CLASSES` and `LIVE` per Repository, and `kubectl get mergepolicy`
shows `CONSUMERS` (the Repositories binding a class policy), `CURRENT` (those serving its current
generation), `LIVE` and `ACCEPTED`; `REPO` is set on a per-repository object only. The
[upgrade](../../docs/upgrading.md#reusable-merge-policies-v04x-release-n) lists the steps.

Helm 3.15 or later: Helm 3.14 assumes Kubernetes 1.29 when it renders offline, so its `helm template`
needs `--kube-version 1.30.0` or later.

## With the umbrella

The `agent-factory` umbrella's subcharts keep their own `crds/` until rollout step 8. Once this
chart is installed it alone manages the CRDs, so skip the umbrella's copies: Argo CD
`skipCrds: true`, or Flux `crds: Skip` on install and upgrade. Plain Helm needs nothing, since it
never upgrades `crds/` and skips a CRD that exists.

## Adopting CRDs that already exist

On a cluster where the CRDs came from the `maku` and `maku-factory` subcharts' `crds/` (any existing
install), Helm refuses this chart: the CRDs exist "and cannot be imported into the current release".
Hand them to the release first, with the release name and namespace you install this chart under
(here `af-crds` in `maku`):

```bash
crds=$(kubectl get crd -o name | grep '\.maku\.ogenki\.io$')
kubectl label $crds app.kubernetes.io/managed-by=Helm --overwrite
kubectl annotate $crds meta.helm.sh/release-name=af-crds meta.helm.sh/release-namespace=maku --overwrite
```

Under Flux, `meta.helm.sh/release-name` must equal the HelmRelease's computed name:
`<targetNamespace>-<name>` when `spec.targetNamespace` is set, `<name>` otherwise, unless
`spec.releaseName` sets it. The release namespace is `spec.targetNamespace`, else the HelmRelease's.

Then install the chart. Existing Rooms and Tasks are untouched. See
[docs/upgrading.md](../../docs/upgrading.md#adopting-the-crds).
